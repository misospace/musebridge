# Marketplace MCP service

A small Model Context Protocol service for exercising Marketplace-shaped integrations. The default `fixture` backend returns synthetic listings only and makes no remote requests; an explicitly selected Facebook backend supports search and listing fetch through a persistent browser session. Its public MCP server identity is `marketplace`. When the opt-in Messenger scope is enabled, a single write-class tool, `messenger_send`, can send a message into a thread once a single-use, issuer-signed approval grant is verified — it confirms delivery by reading the thread for the message's idempotency token (reporting `sent` or `unknown`) and is not yet production-enabled (see "Approval grants and the write path") — while every other tool is read-only.

## Run

Requires Node.js 24.

Run these commands from the repository root:

```sh
npm ci --ignore-scripts
npm run build
npm start
```

`npm start` launches the service from its workspace while keeping the runtime entry at `dist/index.js` inside the service. If a host previously launched the built file directly, update `node dist/index.js` to `node services/marketplace/dist/index.js`. The Streamable HTTP MCP endpoint is `POST /mcp` on `127.0.0.1:8080` by default. Set `HOST=0.0.0.0` when running in a container and optionally override `PORT`. `GET /healthz` is a separate liveness endpoint. The MCP transport is stateless and returns JSON responses; request bodies are limited to 64 KiB. Requests carrying any `Origin` header (including `Origin: null`) are rejected, so this first milestone is server-to-server only.

Build and run the container locally:

```sh
docker build -f services/marketplace/Dockerfile -t marketplace-mcp .
docker run --rm -p 8080:8080 marketplace-mcp
```

GHCR publishes `ghcr.io/misospace/marketplace-mcp` for pushes to `main` and semantic version tags matching `v*.*.*`, after the Node 24 typecheck, lint, test, and build checks pass. The existing version-tag release scheme is retained; image tags (`main`, SHA, and semantic version) remain unchanged. Future image, profile, or tag changes must be coordinated with the service owner. Renovate uses the shared org preset; automatic dependency merges remain disabled for manual review during the fixture milestone.

The service has no built-in authentication. Run it only on a trusted private network and provide network-level access controls before exposing it to other networks. ToolHive can use the service's Streamable HTTP transport at port `8080` and path `/mcp`, but it is not registered with ToolHive yet.

## Tools

- `marketplace_search` requires trimmed, non-empty `query` and `location` strings (each maximum 256 characters). `min_price` and `max_price` must be finite and non-negative with minimum no greater than maximum. `limit` defaults to 5 and must be an integer from 1 through 20. Unknown input keys are rejected.
- `marketplace_search` matches `query` as a case-insensitive substring within the title or the description (a single field, never across the title/description boundary), and matches `location` case-insensitively. Results retain fixture order. Price filters exclude listings whose price is `null`.
- `marketplace_fetch` requires exactly one of `id` or `url`. IDs are bounded, safe identifiers; URLs must be HTTP(S), contain no credentials, and be at most 2048 characters. On the fixture backend, matching strips the fragment and lowercases the host before comparing against fixture URLs (lightweight normalization, not full canonicalization), and never performs network requests. On the opt-in Facebook backend, fetch accepts a numeric listing id or an item URL on the configured Facebook base origin. It extracts only the item id and rebuilds the canonical item URL from that configured base before navigation, so a caller-supplied origin, query string, or fragment is never navigated to. The backend verifies the session through the same fail-closed login, captcha, and checkpoint path as search, then extracts and validates a normalized listing. A page that still renders a complete listing is returned in full, including `state: removed` when Facebook marks it so; `NOT_FOUND` applies only to an unavailable or expired shell that cannot satisfy `Listing` (no usable title, price, or location). A fetched listing can have `state: active`, while search results never do.
- `marketplace_status` accepts `{}`; omitted arguments are also valid and report service `0.1.0`, schema `1.8.0`, and `backend: "fixture"`. It also reports `capabilities`, a non-empty array of `{ surface, provider, backend }` capability surface entries (`marketplace`, `shopping`, `messenger`, `events`, `social`); `backend` is the configured backend name or `null` when the surface is not configured. It also reports optional `shopping_backend`, `events_backend`, and `threads_backend` fields naming the configured backend surfaces, and optional per-surface Facebook session fields `marketplace_session` and `messenger_session` (each `{ status }`, where `status` is `session_unknown`, `session_usable`, `session_needs_reauth`, or `disabled` — `disabled` means no Facebook browser scope drives that surface at all, distinct from an unassessed `session_unknown`). The `capabilities` field is additive in schema `1.2.0`; the `social` capability surface and the optional `threads_backend` field are additive in `1.4.0`; the `messenger_prepare` output contract is additive in `1.5.0`; the `messenger_thread_read` `coverage` field is additive in `1.6.0`; the optional `marketplace_session` and `messenger_session` fields are additive in `1.7.0`, and the legacy `facebook_session` field is kept unchanged as the deprecated alias of the marketplace-scope assessment (when `marketplace_session` reports `disabled`, it keeps the legacy browser-derived value). No existing tool name or field changes.
- `events_search` accepts `{ query, city?, start_date?, end_date?, limit? }`. `query` is a trimmed, non-empty string (maximum 256 characters). `city` is an optional trimmed, non-empty string (maximum 256 characters). `start_date` and `end_date` are optional `YYYY-MM-DD` dates, with `start_date` no later than `end_date`. `limit` defaults to 10 and must be an integer from 1 through 20. Unknown input keys are rejected. Results are read-only availability records: on-sale status, date/time, price ranges, and venue. Events with an unknown start date/time (`starts_at: null`) are excluded from date-bounded searches (when `start_date` and/or `end_date` is supplied) on the fixture path and, per Discovery's local-date filtering, expected to be excluded on the provider path (live validation pending an operator key); they remain visible in unbounded searches and via `events_fetch`.
- `events_fetch` requires exactly one of `id` or `url`. IDs are bounded, safe identifiers; URLs must be HTTP(S), contain no credentials, and be at most 2048 characters. On the fixture backend, matching strips the fragment and lowercases the host before comparing against fixture URLs (lightweight normalization, not full canonicalization), and never performs network requests. On the opt-in Ticketmaster backend, fetch accepts an event id or an https event URL on an allowlist of Ticketmaster regional roots (`ticketmaster.com`, `ticketmaster.ca`, `ticketmaster.co.uk`, `ticketmaster.com.au`, and the other regional roots the provider serves; exact match or any subdomain), extracts the event id, and rebuilds the request against the fixed Discovery API destination. An `http` URL or a lookalike host is rejected and surfaces as the typed error `The Ticketmaster event URL does not contain an event id.` An unknown identifier returns `NOT_FOUND`.
- `threads_posts_list` accepts `{ limit?, since? }`. `limit` defaults to 10 and must be an integer from 1 through 20; `since` is an optional `YYYY-MM-DD` calendar date. It lists the operator's own published Threads posts as a `(threads, default, social)`-scoped read action, returning `posts` plus a `truncated` completeness indicator. On the fixture backend it honors `limit` and `since` (posts with no timestamp are excluded from a `since`-bounded query). Each post's `permalink` is accepted on both Threads web hosts — `threads.net` / `www.threads.net` (legacy) and `threads.com` / `www.threads.com` (Meta's primary host since April 2025) — over HTTPS only; a lookalike host such as `threads.com.evil.example` or an `http://` form is rejected, and the host is never rewritten, since rewriting would fabricate a navigation target. A post with no caption is returned with `text: null` (never an empty string and never a guessed value), because Meta permits image and carousel posts without one; that is not schema drift and never fails the page. `threads_user_id` is the provider's stable `owner.id`, and is `null` when the response has no owner — it is never the mutable `username` handle.
- `threads_replies_list` requires `media_id` (a verified Threads media id) and lists that post's public reply tree as a `(threads, default, social)`-scoped read action, returning `media_id` and `replies` plus a `truncated` completeness indicator. Replies carry the same field contract as posts: `permalink` is accepted on both `threads.net` and `threads.com` (HTTPS only, lookalike hosts rejected, host never rewritten), a reply with no caption has `text: null` rather than failing the page, and `threads_user_id` is the provider's `owner.id` (or `null` when absent, never a username handle). Both tools follow provider cursors for at most 5 upstream pages per call, deduplicate canonical ids across pages while preserving order, and set `truncated: true` when more results may exist beyond the bounded page (a provider cursor remained or the internal page bound was hit) and `false` when the provider page set was exhausted. No DMs, saved items, keyword search, external profile discovery, or publishing exist.
- `messenger_threads_list` accepts `{ limit? }` (`limit` defaults to 10 and must be an integer from 1 through 20). It lists recent conversation threads from the Facebook Marketplace inbox as `(facebook, default, messenger)`-scoped read actions. Threads carry an opaque `thread_id`, an optional bounded `preview` of the last message, and an optional `item_id` extracted from an attached listing link; participant names are not extracted by the Facebook backend. On the fixture backend it returns synthetic conversations. The listing is bounded-recent and says so: the result carries an explicit `truncated` indicator — `true` when more threads were left behind than returned (verified cursor-chain ids beyond the collector cap or beyond the caller's `limit`, or the bounded DOM fallback with rows beyond the limit or at its collection bound), `false` only when the provider set behind this listing was proven exhausted. GraphQL thread ids are returned only from a fully observed cursor chain, and an unverifiable chain stays a typed `UPSTREAM_ERROR` rather than a partial listing (#151). The field is absent only when a host-injected backend predates this additive field and still returns a bare thread array; an absent field is unknown coverage, never a claim that the listing is complete.
- `messenger_thread_read` requires `thread_id` (a bounded safe identifier). It reads one conversation's messages: `sender` (`you`/`other`), optional `sender_name`, bounded `text`, and optional `sent_at`. The read window is bounded and anchored on the newest end of the thread: `coverage` (additive in schema `1.6.0`) reports `window: "tail"` — the newest end was established by the explicit timestamps on the message rows, never by DOM order, and the rendered rows were provably the whole message set the page declared — `scanned_rows`, and `truncated: true` when messages existed outside the returned window, so an idempotency token absent from the window is never proof of an unsent message. When that newest end cannot be established from explicit timestamps and the page's declared set size, the read fails closed with a typed `UPSTREAM_ERROR` rather than returning a window. The thread URL is rebuilt from the configured Facebook base origin, so a caller-supplied URL is never navigated. On the fixture backend, an unknown `thread_id` returns `NOT_FOUND`.
- `messenger_prepare` requires `thread_id` (a bounded safe identifier) and a non-empty `message` (same bounds as `messenger_send`: maximum 2,000 characters, single-line; control characters are rejected). It is a `prepare`-class action on the `(facebook, default, messenger)` scope: it runs autonomously, requires no approval grant, sends nothing, and grants no approval. It mints the idempotency token first, builds and validates the complete `messenger_send` payload `{ thread_id, message, idempotency_token }` from it, and only then digests that validated payload, so the returned `subject_digest` is exactly what a later `messenger_send` authorization is checked against. The result is a draft: `status: "draft"`, `sent: false`, the counterparty `participant` (`null` when no counterparty name is attributed to the thread, never a fabricated handle), the authored `draft_message`, the `rendered_message` that would actually be posted (`draft_message [idempotency_token]`, the same form `messenger_send` delivers), a `counterparty_marker` disclosure confirming the marker appears exactly once in the message the counterparty will see, the `idempotency_token`, the canonical `send_input`, and `subject_digest`. Each call mints a fresh token and digest. Passing `send_input` back unmodified into `messenger_send` therefore matches the published digest; changing the text, thread, or token changes it. On the Facebook backend this reads the thread to resolve the counterparty, so it carries the same "Seen" side effect already documented for `messenger_thread_read` and the same fail-closed behavior: a thread whose newest end cannot be proven yields a typed `UPSTREAM_ERROR` instead of a draft. On the fixture backend, an unknown `thread_id` returns `NOT_FOUND`. `messenger_prepare` is advertised only where the configured conversation backend actually implements `prepareDraft`, and `messenger_send` only where it implements `sendThread`; a host-injected backend that serves conversation reads without them keeps its reads, and the unserved tool is unknown rather than failing at call time.
- `messenger_send` requires `thread_id` (a bounded safe identifier), a non-empty `message` (maximum 2,000 characters, single-line; control characters are rejected), and `idempotency_token` (16–128 characters). It is a `send`-class action on the `(facebook, default, messenger)` scope: it never runs autonomously. It executes only after a single-use approval grant is presented through the host and passes the `HmacGrantAuthorizer` (issuer-signature plus scope/action/payload-digest/expiry checks); a missing or invalid grant fails closed with `APPROVAL_REQUIRED`, and a signature that does not verify or a grant already consumed fails with `ACTION_FORBIDDEN`. Delivery is not inferred from the send call returning: after a resolved send, or a failure that timed out or was interrupted after its submit (Enter) was dispatched (tagged `submit_triggered` by the Facebook backend), it performs exactly one thread read and reports `status: "sent"` only if a message attributed to the local sender (extracted `sender: 'you'`) contains the bracketed `` `message [idempotency_token]` `` form, otherwise `status: "unknown"` (still `ok: true`); it never resends. On the fixture backend the read-back contains the token, so a completed send reports `sent`.
- Successful search and fetch results include the configured backend `name`; `marketplace_status` reports that same identity. The built-in backend is named `fixture`. Backend names must be non-empty strings of at most 64 characters. The schema version is `1.8.0`; additive output changes bump the minor version. The `messenger_threads_list` `truncated` completeness indicator was added additively in schema `1.8.0`. The per-surface `marketplace_session`/`messenger_session` status fields are additive in `1.7.0`. The `messenger_thread_read` `coverage` field is additive in `1.6.0`. The runtime failure code `SURFACE_DISABLED` was added additively in schema `1.3.0`.
- Unknown but valid fetch identifiers return a `NOT_FOUND` runtime envelope. Invalid tool arguments are JSON-RPC `InvalidParams` errors, not tool-error envelopes.

Listing records use `images` (an array of at most six HTTP(S) URLs), required nullable ISO date-time fields `posted_at` and `updated_at`, and required nullable `seller`. Seller details are bounded and optional within a non-null seller object. `state` is one of `active`, `sold`, `pending`, `removed`, or `unknown`. The fixed fixtures use `example.com` URLs and include removed, pending, sold, unknown-state, and null-price examples.

Backends may throw the exported `ProviderError` class to return a known runtime failure. Supported codes are `AUTH_EXPIRED`, `LOGIN_REQUIRED`, `CAPTCHA_REQUIRED`, `SESSION_INVALID`, `RATE_LIMITED`, `UPSTREAM_ERROR`, and `TIMEOUT`; messages and optional metadata (`action_required`, HTTP(S) `login_url`, and non-negative integer `retry_after` seconds) are validated and bounded. Only valid `ProviderError` instances are exposed to callers. Unexpected errors and malformed provider errors are logged server-side and reduced to a generic `INTERNAL_ERROR` envelope. A fetch miss remains `NOT_FOUND`.

Each search/fetch backend call has its own deadline, defaulting to 30,000 ms. Override it with `BACKEND_TIMEOUT_MS` or the `backendTimeoutMs` service option; values must be positive integers below 60,000 ms. The backend receives an `AbortSignal` that aborts on deadline, MCP request cancellation/disconnect, or service shutdown. A backend must cooperate with this signal to stop its underlying work: the service can stop awaiting an arbitrary non-cooperative promise, but cannot forcibly cancel the work itself.

### Shopping surface

Shopping is read-only and defaults to synthetic fixture offers. Set `SHOPPING_BACKEND=ebay` to opt into eBay; configure `EBAY_CLIENT_ID` and `EBAY_CLIENT_SECRET` as environment variables. The eBay API destination is not operator-configurable — the client only talks to eBay's production or sandbox hosts over HTTPS, or a loopback address when a test injects one, because the token request carries application credentials. Offers contain seller-controlled content and must be treated as untrusted. This surface never adds cart, checkout, or bid writes. Shipping figures are as listed by the seller — they are not destination-validated landed costs.

### Events availability surface

Events availability is read-only and defaults to synthetic fixtures. Set `EVENTS_BACKEND=ticketmaster` to opt into the Ticketmaster Discovery API v2 and configure `TICKETMASTER_API_KEY` as an environment variable. The API destination is not operator-configurable: the client only talks to `app.ticketmaster.com` over HTTPS, or a loopback address when a test injects one, because the API key travels as a query parameter. Event names, venues, and classifications are provider content and must be treated as untrusted. This surface never books, reserves, or purchases anything. The Discovery API reports event-level on-sale status and price ranges only — never seat-level inventory — so a live event is never reported `sold_out`; that status is fixture-only.

### Threads (Meta) social surface

Threads is read-only and defaults to synthetic fixtures. Set `THREADS_BACKEND=threads` to opt into the official Threads Graph API. It exposes two read-only tools on scope `(threads, default, social)`: `threads_posts_list` (`{ limit?, since? }`) lists the operator's own published posts, and `threads_replies_list` (`{ media_id }`) lists the public reply tree for one verified media id. Both return `{ ok, backend, …, truncated }`; `truncated` is `true` when more results may exist beyond the bounded page (a provider cursor remained or the internal page bound was hit) and `false` when the provider page set was exhausted. Cursor following is bounded to at most 5 upstream pages per call, and canonical ids are deduplicated across pages with order preserved. No DMs, saved items, keyword search, external profile discovery, or publishing are available.

Credentials are `THREADS_ACCESS_TOKEN` and `THREADS_USER_ID`. They are environment-only, read at assembly time, and never logged or returned in tool output; the token travels as `Authorization: Bearer …` only to the pinned `https://graph.threads.net` destination, with a loopback address accepted solely as an explicit test seam — no environment variable can move the credential destination.

The live backend is gated on two parts, checked in order. First, `THREADS_ACCESS_TOKEN` and `THREADS_USER_ID` must both be non-empty; a missing token or user id is a startup failure (typed `RangeError`), not a silent empty success. Second, `THREADS_LIVE_VALIDATED=1` must be set: this is an explicit operator acknowledgement that the connector was validated against the current Meta reference, and it exists so a live connector is never enabled merely by supplying credentials. Its absence is also a startup failure, with a typed `RangeError` naming `THREADS_LIVE_VALIDATED`. The fixture backend stays the default.

The connector fails closed. A `data` array containing a malformed or schema-drifted item throws `ProviderError('UPSTREAM_ERROR', …)` — never a silent empty success — and a non-array `data` likewise; a legitimate `{data: []}` is an empty success. HTTP 401/403 map to `AUTH_EXPIRED`, 429 to `RATE_LIMITED` with a bounded `retry_after`, and a deadline or cancellation to `TIMEOUT`. On the fixture backend, `limit` and `since` are honored (calendar-date compare; posts with no timestamp are excluded from a `since`-bounded query).

URL hosts are policed in two layers. A post or reply `permalink` is a navigation target the provider published, so it is accepted only over HTTPS on the exact Threads hosts `threads.net` / `www.threads.net` and `threads.com` / `www.threads.com`; a lookalike such as `threads.com.evil.example` or `notthreads.com`, a suffixed variant, or an `http://` form is schema drift and fails the page. `media_urls` is the wider display-URL allowlist, bounded to six entries: those same exact Threads hosts plus Meta's media CDN roots (`cdninstagram.com` and its subdomains, `fbcdn.net` and its subdomains), still HTTPS-only, because live `media_url` / `thumbnail_url` values are expected to be served from them. A media URL on any host outside that allowlist is dropped — never returned, rewritten, or substituted — and the rest of the post is still returned; the deliberate consequence is that a dropped media URL is indistinguishable from a post that carried none, so `media_type` may still read `IMAGE` beside an empty `media_urls`. Media in a reply tree is third-party-authored content that happens to sit on a Meta host: an allowlisted host is not a trust signal, and the URLs are returned bounded and untrusted. Hosts are never normalized or rewritten in either layer. Output follows the schema contract shipped in `1.4.0`, unchanged by the additive `1.5.0` bump; the `social` capability surface and the optional `threads_backend` status field shipped additively in `1.4.0`, and the Threads tools request `owner` so `threads_user_id` maps from the provider's stable `owner.id`.

**Operator setup**

1. Keep the default `fixture` backend and provide `THREADS_ACCESS_TOKEN` and `THREADS_USER_ID` as environment variables (both required; the token needs the permissions your reads require).
2. Confirm the current Meta reference out-of-band: check the endpoint paths, permission names, and response shapes this connector documents against Meta's current Threads API reference.
3. Set `THREADS_BACKEND=threads` and `THREADS_LIVE_VALIDATED=1` to activate the live backend, then run the single authorized live read in the checklist below.

**Live-validation checklist**

- With the live backend active, run exactly one `threads_posts_list` for the operator's own posts and one `threads_replies_list` for one of those media ids.
- Confirm the requested `fields` projection is accepted as sent — including `owner`, which `threads_user_id` is mapped from. An unsupported field makes every live read fail with `UPSTREAM_ERROR`, so if a read errors on the projection, unset `THREADS_LIVE_VALIDATED` and reconcile the field list against Meta's current reference before retrying.
- Do not post, reply, or send anything: this surface has no write path, and no private messages or DMs are read.
- If the observed shapes differ from the documented fields, unset `THREADS_LIVE_VALIDATED` and treat the connector as unverified until the reference is reconciled.

The endpoints and field shapes are documented but unverified against the current Meta reference — keep the connector pointed at `graph.threads.net` and the documented fields list. Deliberate gaps in this wave: no publishing, no DM, no saved items, no keyword search, no external profile discovery, and no Instagram connector. See [`docs/instagram-threads-consumer-research.md`](../../docs/instagram-threads-consumer-research.md) for the capability matrix and [`docs/provider-architecture.md`](../../docs/provider-architecture.md) for the provider layout.

## Browser runtime

The service includes a minimal Chromium session layer backed by the pinned Playwright package. Each session scope lazily starts its own browser with a persistent profile — the marketplace scope at `BROWSER_PROFILE_DIR` (default `$HOME/.marketplace/browser-profile`), the opt-in messenger scope at `MESSENGER_PROFILE_DIR` (default `$HOME/.marketplace/browser-profile-messenger`) — and serializes browser work through one page at a time per scope. An invalid `BROWSER_PROFILE_DIR` fails service startup. Browser operations use the same `AbortSignal` and deadline path as backend work. An in-progress browser launch cannot be aborted mid-launch (Playwright exposes no signal for it): it is bounded by the launch timeout, defaulting to 30,000 ms, and the signal is honoured immediately before and after the launch. Non-cancellable infrastructure steps (page creation and page/context teardown) are bounded by a settle timeout, defaulting to 5,000 ms, so an unresponsive browser cannot wedge the serialized queue. If the timeout expires during page creation or page teardown, the current browser context is discarded and the session is marked unavailable; the next operation waits for teardown to settle and relaunches a clean context rather than continuing against a potentially unhealthy browser. Chromium runs as the non-root container user. Credentials are supplied only through the environment and are never persisted by this service; cookies, localStorage, headers, page content, and profile contents are never logged. Do not set `PWDEBUG` or `DEBUG=pw:*` in production: Playwright debug logging can include page content. No CDP endpoint is exposed. The Facebook session probe and opt-in Facebook backend use the marketplace scope's browser for search and fetch; the fixture backend does not. The messenger scope's probe, credential login, and conversation backend use the messenger scope's browser.

Container users should mount a persistent volume at the profile directory and run Chromium with `--init --ipc=host`, following Playwright's Docker guidance.

### Facebook session probe

`FacebookSessionProbe` in `src/facebook.ts` composes over the serialized browser manager. `probeSession(signal)` loads the Marketplace entry point and reports `session_usable` for an authenticated Marketplace page, `session_needs_reauth` for a login page or redirect (`LOGIN_REQUIRED`), checkpoint/challenge (`SESSION_INVALID`), or captcha (`CAPTCHA_REQUIRED`). `session_unknown` means no verdict is available for the current probe: the session has never been probed, the page is ambiguous, an in-flight probe is cancelled, or loading fails. A probe cancelled before it starts leaves the previous assessment untouched. Do not read `session_unknown` as "not usable"; only `session_usable` asserts an authenticated Marketplace.

Classification uses the final URL and a small set of semantic signals: a password field or login form, checkpoint form or copy, captcha frame or copy, an authenticated marker (account/profile label or logout affordance), a login prompt, and a main landmark plus a Marketplace link. It does not depend on hashed CSS classes. The default origin is exactly `https://www.facebook.com`. The probe never automates login, stores or exports credentials, or logs page HTML, cookies, storage, headers, form values, or screenshots. Credential submission is a separate, opt-in step (see below); the no-logging rule applies to it unchanged.

The origin can be injected only through the constructor for tests (or the service's `facebookBaseUrl` option); it is not an environment variable or tool input. It must be exactly `https://www.facebook.com` or a loopback test origin (`localhost`, `127.0.0.1`, or `::1`, over HTTP or HTTPS); any other origin is rejected, so this seam cannot reach an arbitrary host. A redirect to any other origin, including another Facebook subdomain, deliberately produces `session_unknown` rather than `session_usable`. `marketplace_status` reports the per-surface fields `marketplace_session: { status }` and `messenger_session: { status }` — each profile's last known assessment (`session_unknown`, `session_usable`, `session_needs_reauth`, or `disabled` for a surface with no Facebook browser scope) — without doing browser work, so a Messenger profile that needs re-auth never hides behind a healthy Marketplace report. A cached `session_usable` is never a stale claim: any auth-class observation (a login requirement, captcha, or checkpoint) on a search, fetch, inbox, or thread page immediately downgrades that scope's cached assessment to `session_needs_reauth`, and only a fresh probe or completed re-auth records `session_usable` again. The legacy `facebook_session: { status }` field remains as the deprecated alias of the marketplace-scope assessment. These fields are additive: the contract reported `schema_version` `1.7.0` (and `1.8.0` since the additive `messenger_threads_list` `truncated` indicator), and no tool name or existing field changed.

The Facebook backend is opt-in; `MARKETPLACE_BACKEND` defaults to `fixture`. Set `MARKETPLACE_BACKEND=facebook` or pass `backendKind: 'facebook'` to select it. The backend implements search and listing fetch. It verifies the session before each operation and fails closed when the probe returns `session_unknown`; a plain `LOGIN_REQUIRED` verdict triggers the credential login below when credentials are configured.

Search URLs follow `/marketplace/<slug>/search/?query=` (with optional `minPrice` and `maxPrice`). The built-in map covers ten US metro markets, all in USD; callers can supply an explicit replacement market map through `facebookMarkets`. Locations must resolve through a configured label, slug, or alias. Unknown and ambiguous locations return a typed error, and slugs are never guessed.

For deployment-time configuration, set `FACEBOOK_MARKETS_FILE` to a mounted JSON file holding an array of markets, for example `[{"slug":"calgary","label":"Calgary, AB","currency":"CAD","aliases":["calgary alberta"]}]`. The file *replaces* the built-in map rather than adding to it, so leave it unset to keep the defaults; an empty value counts as unset. It is read once and validated at startup, whether or not the Facebook backend is selected, so a misconfigured file fails the process rather than surfacing on the first search. An unreadable or non-regular file, invalid JSON, an unknown key, an entry that breaks the same rules as the built-in map, a duplicate slug, or a label or alias that maps to two different markets all fail startup; the error names the file and, for a per-entry defect, the entry's index. `MARKETPLACE_MARKETS_FILE` is the name this first shipped under and still works as a fallback, but it is deprecated in favour of `FACEBOOK_MARKETS_FILE`.

The parser never synthesizes an item id, never marks a search card `active`, leaves relative timestamps as `null`, always sets `updated_at` to `null`, and uses only the first price token. For fetched listings, currency must come from an explicit marker in the price text or from a configured market resolved using the listing's own extracted location; otherwise the fetch fails closed with `UPSTREAM_ERROR` rather than guessing from an arbitrary configured market. A search reads one page only: it does not scroll or paginate. Login, captcha, invalid session/checkpoint, rate limit, timeout, and unrecognized/invalid upstream pages return bounded typed provider errors; only a recognized no-results page becomes an empty success. These errors do not expose page text, card contents, hrefs, images, cookies, or storage.

### Facebook credential login

`FacebookCredentialLogin` in `src/facebook-login.ts` is the opt-in path that replaces manual VNC re-auth as the normal way a logged-out session recovers. It is deliberately separate from the probe, which still only classifies state.

When `MARKETPLACE_BACKEND=facebook` and the probe reports `LOGIN_REQUIRED`, the backend submits credentials if they are configured: it loads Facebook's regular login page, enters `FACEBOOK_USERNAME` into `input[name="email"]` and `FACEBOOK_PASSWORD` into `input[name="pass"]`, and submits by pressing Enter, because Facebook no longer renders a login button. It then polls the same page classification every 2 seconds for up to `FACEBOOK_LOGIN_WAIT_SECONDS` (default 180) while the login is approved from the Facebook mobile app. This independent wait survives an individual search's shorter backend deadline; that search returns the ordinary backend deadline error (`TIMEOUT`) if its budget expires, while the single in-flight login continues for later requests. Approval may land on any authenticated same-origin page: the login navigates to Marketplace and classifies there before reporting success. Only the backend's confirming probe records `session_usable`. The authenticated profile is persisted by the existing persistent-profile volume, so later searches skip the login entirely.

Credentials are optional and environment-only:

- `FACEBOOK_USERNAME` / `FACEBOOK_PASSWORD` — set together or not at all; a half-configured pair fails startup once the Facebook backend is selected. They are read only for that backend, so a fixture deployment never touches them. They are never written to disk, returned in a tool result, placed in a URL, or logged. A login is attempted only for a plain login requirement.
- `FACEBOOK_LOGIN_WAIT_SECONDS` — how long to wait for the mobile approval, as a positive integer. Defaults to 180.

Credential retry cooldown applies account-wide across Marketplace and Messenger and cannot be tuned by environment variables (30-second base, doubling with each further failure in the scope that failed; the third consecutive failure in a scope hard-opens the gate and holds that scope back for the ladder's 10-minute ceiling cooldown). The gate itself is shared account-wide — one in-flight attempt, one cooldown window that holds credential attempts in both scopes back, and a hard open that blocks every scope — while each scope owns its own failure count, cooldown deadline, and unverified claim, so only that scope's probe-verified usable session clears its own penalty, and only the scope that hit a challenge or the failure threshold clears the account-wide hard open; another scope's usable session leaves it standing, so that scope's profile has to be re-authenticated through the manual re-auth console below. A captcha or checkpoint seen during a credential attempt hard-opens the gate for every scope; a captcha or checkpoint seen by the session probe, whether the initial probe or the confirming probe after a login attempt, never triggers a further credential submission and hard-opens the gate for every scope as well; and a captcha or checkpoint observed on a Marketplace result or item page or a Messenger inbox or thread page — including the `messenger_send` pre-submit verification page — hard-opens the gate for every scope too, because a page the session loaded is as much a fact about the account as a probe result. A plain login requirement observed on a page downgrades the cached assessment but does not hard-open the gate: a plain login stays the recoverable credential path's business. The scope that first observed the challenge owns that open: a later observer does not take ownership, so its verified usable session does not close the open, and only the owning scope's probe-verified usable session can close it. A challenge recorded while a credential attempt is in flight aborts that attempt before it can submit further credentials; the gate arms the revocation of a granted attempt atomically with the grant, so a challenge recorded in the window between the grant and the start of the attempt also prevents any credential submission, and the revoked attempt is abandoned rather than counted as a failure. A manual re-auth lease that takes a browser profile over ends the credential attempt that is still in flight on it the same way: the preempted attempt submits no credential, it is abandoned rather than counted as a failure, and the takeover never hard-opens the gate, so the takeover itself costs the account no retry budget. Manual re-authentication is unaffected. The in-memory breaker exposes only its status and failure count, never credentials. An attempt that self-reports a successful approval but is never followed by a probe-verified usable session counts as a failed cycle for the next attempt, so unverified successes cannot unlock unlimited retries either.

This is not a 2FA implementation and it bypasses nothing. A captcha stops the attempt immediately, because it cannot be satisfied from the phone. A checkpoint is tolerated while the window is open — Facebook uses one as the gate for the approval itself — and reported as `SESSION_INVALID` only once the window closes. Either outcome, and a timeout, leaves the session `session_unknown` or `session_needs_reauth`, never usable, and hands off to the manual re-auth console below. Credentials are submitted at most once per attempt; a challenge never triggers a retry.

Playwright's error text from the credential step is deliberately not surfaced: an error raised while typing can quote the typed value, so only the error name is logged.

### Messenger surface (conversation reads and sends)

For a session-classification investigation, set `FACEBOOK_MESSENGER_PROBE_ONLY=1`.
Both conversation tools then run only the isolated Messenger session probe: no credential
login, inbox extraction, or conversation navigation follows, even if the probe is authenticated.
The tool returns a typed error with code `SURFACE_DISABLED` while this setting is enabled. Remove it only after the
classification is understood. The setting accepts `0` or `1`; other values fail startup.

Messenger probes emit one `Facebook Messenger probe diagnostics:` record containing only
structural booleans. CAPTCHA iframe URL matches, element ID matches, test-ID matches, and
challenge-text matches each have separate `Matched` and `Visible` flags, alongside matched
and visible authenticated markers and main landmarks. No provider text, DOM attributes,
URLs, identifiers, cookies, or credentials are recorded. `Visible` means a non-empty rendered
box with visible CSS and no fully transparent ancestor; it does not prove a widget is active,
unobscured, or within the viewport. A visible matching signal remains `CAPTCHA_REQUIRED`;
hidden-only signals remain `session_unknown` and fail closed without triggering credential
login. Visibility diagnostics do not relax authentication requirements or authorize reads.

When `MARKETPLACE_BACKEND=facebook` and `MARKETPLACE_MESSENGER=1`, the service instantiates a second, fully isolated session scope `(facebook, default, messenger)`: its own persistent browser profile (`MESSENGER_PROFILE_DIR`), its own session probe (classifying from the inbox landing `/marketplace/inbox/` with the same fail-closed login/checkpoint/captcha signals), and — when credentials are configured — its own single-in-flight credential login instance. The same `FACEBOOK_USERNAME`/`FACEBOOK_PASSWORD` pair is reused because it is the same identity; the isolation is between browser profiles and session assessments, not between identities. A messenger-scope browser launches only when a conversation tool is called.

`messenger_threads_list` reads the Marketplace inbox page (`/marketplace/inbox/`); `messenger_thread_read` reads one thread page (`/messages/t/{thread_id}/`, rebuilt from the configured base). Extraction accepts only accessibility-contract signals — thread anchors with `/messages/t/{id}` hrefs, `role="row"` message rows with `You said:` / `{Name} said:` aria-label patterns, and `time[datetime]` timestamps — and fails closed: an authenticated page with neither recognizable content nor a recognized empty state is a typed `UPSTREAM_ERROR`, never an empty success or fabricated data. Message rows without a recognizable orientation marker are skipped rather than attributed. The rows are collected from one scope only: the page's message log when exactly one log renders rows, and otherwise — on a page with no message log — the one container that holds the rendered rows (their nearest common ancestor). Rows the page renders beside the message log never enter the collection, so a second row group cannot contribute to the thread; on a page with no message log, the page's own set accounting is the only discriminator between the conversation's rows and another set's, so a row group that declares a consistent set of its own is taken as the conversation. Only the message log's own counters are read as the scope's set accounting — a plain container is not a set container — while a row's parent `aria-rowcount` remains the standard counter for a grid, table or treegrid. A page that renders more than one log with rows, or whose rows share no common container other than the document and no single common parent, is an unrecognized layout: it yields no rows at all, so the read fails closed with a typed `UPSTREAM_ERROR`. The bounded message window is anchored on the newest end of the thread, and that end is established **only** by the explicit `time[datetime]` timestamps carried on the message rows themselves: DOM order is never used to decide which end is newest, and the returned window is ordered by those timestamps rather than by the order the rows happened to render in, because the deployed Messenger DOM ordering is unvalidated. Every attributed message row must carry its own explicit `time[datetime]` marker — a timestamp on a nested element inside the row is not the row's own — and every rendered message row is examined for it, up to a scan bound of 500 rendered rows. The rendered rows must also be provably the whole message set: a virtualized message log can render only a window of the thread, and that window can omit the newest messages entirely, so examining every rendered row proves only that the rendered subset was examined. The page's own accessibility set accounting is the observable statement of how many items the set holds — `aria-setsize` on the message rows or on the message log, `aria-rowcount` on a grid, table or treegrid — and every rendered row must attest that it belongs to that set, by declaring that set's size itself or, when every rendered row declares a position, by declaring an `aria-posinset` inside it. A row that attests nothing belongs to some other set, so it is never counted toward the set's completeness. A window is certified only when the page declares one size for the scope, every rendered row attests that it belongs to that set, the rendered rows are as many as the declared set, and the declared positions — when present — are distinct and reach the end of the set. The read fails closed with a typed `UPSTREAM_ERROR` when an attributed row carries no usable timestamp of its own, when the scan did not examine every rendered row, when the read collected more candidate text than its 512,000-character budget, when the extraction cannot report its scan bounds, when the page reports no size for its message set, or when the rendered rows are only part of the set the page declares, because in each case the newest end of the thread cannot be proven and the read never guesses an end. A proven window holds the newest messages by timestamp, is reported oldest-first, and `coverage` states `window: "tail"`, `scanned_rows`, and `truncated: true` when older messages existed outside the returned window. Messages that share one timestamp keep the order they were rendered in. Coverage describes the message set the page declared and the read examined, not the provider's total history. Because navigation follows redirects, a page is only trusted at its expected address: the inbox must be reached at the configured inbox path, and a thread must be reached at the requested thread id — a redirect to another conversation or page is a typed `UPSTREAM_ERROR`, never content attributed to the wrong thread.

**Reads are not perfectly invisible.** Opening a thread marks it "Seen" for the other participant, and the visit may surface presence — an intrinsic property of the only available access path (there is no side-effect-free browser way to read a Messenger thread). This is a named, operator-approved exception to the side-effect-free `read` definition in the boundary contract; Miso must treat thread reads as visible to the counterpart. `messenger_threads_list` reads the inbox page without opening threads and does not generate receipts.

The real Messenger/Marketplace-inbox DOM contract is **not yet validated against the live site** (this repo's tests are synthetic-only by policy). The contract above is written from public documentation and research; see [`docs/conversation-surface-research.md`](../../docs/conversation-surface-research.md) for what is verified versus assumed and the validation plan. The live validation must confirm the explicit `time[datetime]` markers each message row carries itself — a nested element's timestamp is not the row's own — that the timestamp-proven newest window depends on; without them the read fails closed rather than guessing an end. It must equally confirm the accessibility set accounting the completeness proof depends on: whether the deployed message log declares the size of its message set (`aria-setsize` on the rows or the log, `aria-rowcount` on a grid, table or treegrid), whether each rendered row declares that set's size or its own position in it, and whether the deployed log renders the whole thread at all. Without a declared set size, or without every rendered row attesting that it belongs to it, the read fails closed rather than certify a rendered window as the thread's newest end. Until that validation passes, treat these tools as contract-shaped but unproven in production — the fixture backend provides stable synthetic data for integration testing.

The messenger scope has its own interactive re-auth loop, separate from the marketplace scope's: it is a distinct `ReauthManager` driving the messenger profile, landing on the messenger inbox path (`/marketplace/inbox/`) by default — the same landing as the messenger session probe — because `/messages/` auto-opens a thread and can send a visible Seen receipt, with its own loopback admin port (`MESSENGER_REAUTH_ADMIN_PORT`, default 8788) and optional viewer port (`MESSENGER_REAUTH_VIEWER_PORT`), so a captcha or checkpoint on the messenger profile is recoverable through the loopback console without touching the marketplace session. The `messengerReauthTargetUrl` service option is an opt-in override for this landing, and its side effects are the operator's responsibility. `messenger_send` runs on this scope. Thread previews and message texts are seller-controlled content returned verbatim within bounds; interpreting them is the caller's job, and they must be treated as untrusted input.

## Manual re-auth console

When a provider reports `LOGIN_REQUIRED`, `CAPTCHA_REQUIRED`, or `SESSION_INVALID`, an operator can temporarily take over the persistent browser profile and complete the challenge manually. This console is an operator-only side channel; it is not exposed through any MCP tool and does not change the tool contract.

The loopback-only admin listener provides three JSON endpoints:

- `POST /reauth/start` starts or returns the active lease.
- `GET /reauth/status` reports the current lease state.
- `POST /reauth/stop` ends the lease and returns the idle state.

Successful responses have the shape `{ "phase": "active", "lease": { "id": "...", "startedAt": "...", "expiresAt": "...", "consoleUrl": "http://127.0.0.1:.../vnc.html?...#password=...", "viewerPort": 6080 }, "expiresAt": "...", "remainingMs": 600000 }`. Idle responses use `"phase": "idle"`, `"lease": null`, and null `expiresAt` and `remainingMs`. Failed operations return a generic JSON error without exposing internals.

Configuration is through environment variables: `REAUTH_ADMIN_PORT` defaults to `8787`, `REAUTH_VIEWER_PORT` defaults to `6080`, and `REAUTH_LEASE_MS` defaults to `600000` (10 minutes). The messenger scope's loop uses its own variables, `MESSENGER_REAUTH_ADMIN_PORT` (default 8788) and `MESSENGER_REAUTH_VIEWER_PORT` (default auto-allocated), so its admin and viewer ports differ from the marketplace scope's; it lands on the messenger inbox path by default (avoiding the Seen-receipt risk of `/messages/`, which auto-opens a thread), and the `messengerReauthTargetUrl` service option is an opt-in override whose side effects are the operator's responsibility. A lease must be a positive safe integer and cannot exceed `1800000` ms (30 minutes). The service options provide internal constructor/test seams for custom targets and runtimes; these are not environment variables or request inputs.

The intended access path is `kubectl port-forward` for both the admin and viewer ports, then use the returned console URL from the operator's local machine. This admin interface is intentionally unauthenticated because both listeners bind only to `127.0.0.1`; never expose either port through a Kubernetes Service or Ingress. This project ships no Kubernetes manifests. In a container, configure port-forwarding to the pod's admin and viewer ports without changing their loopback binds.

Each lease takes exclusive ownership of the scope's browser profile it belongs to, so ordinary browser work on that scope fails fast instead of queueing until the lease ends; the marketplace lease owns the marketplace profile and the messenger lease owns the messenger profile, and the two loops are independent. A lease also ends the automated credential attempt that is still in flight on the profile it takes over: the preempted attempt submits no credential it has not already submitted — a credential submitted before the lease began cannot be undone — and is abandoned rather than counted as a failure, and the request that was waiting on it fails with `UPSTREAM_ERROR` ("The browser session is not available."). The console password is ephemeral and delivered only in the URL fragment, which browsers do not send to the viewer's HTTP access log. The password is held only for the lease; its file is mode `0600` inside a private temporary directory, and the directory and file are removed at teardown. Credentials and page content are never logged or stored by the service, and no CDP/remote-debugging endpoint is exposed. Closing the console does not mean the session is authenticated: stopping a lease resets the assessment to `session_unknown`, and the next ordinary probe must verify the session again.

## Approval grants and the write path

`messenger_send` is the only write-class tool; `messenger_prepare` is prepare-class (autonomous, no grant, sends nothing), and every other tool is read-only. Write-class actions never run autonomously and dispatch is fail-closed through the authorization gate.

Production verification is the `HmacGrantAuthorizer`. It accepts a grant as a `signedGrantEnvelopeSchema` envelope — the grant fields plus a `signature`, which is the lowercase hex HMAC-SHA256 of the grant's canonical (key-sorted) form under a shared issuer secret — and authorizes the action only when the signature matches, the grant's `provider`/`account`/`surface`/`action` match the request, its `subject_digest` matches the validated payload, it is unexpired, and it has not already been consumed. A verified grant is consumed in the same step that authorizes the action, so it authorizes exactly one execution and replay fails.

The authorizer is installed only when a grant-issuer secret and durable single-use consumption state are both configured. The secret is the `grantIssuerSecret` service option or the `GRANT_ISSUER_SECRET` environment variable, read at assembly time and never logged. Durable state is the `grantConsumptionStore` service option or, when that is absent, a `FileGrantConsumptionStore` built over the `GRANT_STATE_PATH` directory (a claim is a file created exclusively for the grant id, recording its expiry; expired entries are pruned). With a configured secret but no durable state, the service installs a deny-all authorizer and logs one static startup warning (never the secret) rather than weakening single-use enforcement; with no secret at all it likewise installs a deny-all authorizer — either way every write fails closed with `APPROVAL_REQUIRED`. Approvals are owned by Miso/OpenClaw and are never self-issued: grants reach the service only through the host (`approvalGrant` service option or the equivalent host channel), never as tool arguments. A grant whose fields match but whose signature does not verify is refused with `ACTION_FORBIDDEN`, as is a grant that has already been used.

Real-send enablement is deferred. A standalone Musebridge process has no path to present a grant — grants arrive only via the embedding host's `approvalGrant` callback — and a real production send additionally requires live Messenger DOM validation (the existing caveat in the Messenger surface section above); `messenger_prepare` has shipped and issues no send. Until durable grant state is configured, a trusted host approval integration supplies grants, and the DOM contract is validated, `messenger_send` fails closed.
