# Marketplace MCP service

- Node.js 24 ESM TypeScript workspace named `marketplace-mcp`. Keep the build output entry at `services/marketplace/dist/index.js`.
- The service owns `services/marketplace/package.json`, `services/marketplace/tsconfig.json`, `services/marketplace/tsconfig.test.json`, `services/marketplace/src/**`, `services/marketplace/tests/**`, `services/marketplace/scripts/**`, `services/marketplace/README.md`, and this file. The root owns the single `package-lock.json`; coordinate container/CI changes with their owner and do not rewrite unrelated files.
- Validate tool inputs strictly with Zod and return malformed arguments as JSON-RPC `InvalidParams`. Preserve the public names `marketplace_search`, `marketplace_fetch`, and `marketplace_status` and the versioned consumer listing contract.
- Every registered tool declares an action risk class and scope, and dispatch is fail-closed through `authorizeAction`. Write-class tools require a single-use approval grant verified by an injected authorizer; approvals are owned by Miso/OpenClaw and never self-issued, and high-consequence actions are refused unconditionally. Production verification is `HmacGrantAuthorizer`: it accepts a `signedGrantEnvelopeSchema` envelope whose HMAC-SHA256 signature over the grant's canonical form matches the shared issuer secret, whose scope/action/payload-digest match the request, that has not expired, and that has not been consumed; the verification and the single-use consumption claim run in one synchronous step. Consumption is a `GrantConsumptionStore` seam — `claim(grantId, expiresAt)` is an atomic, synchronous check-and-set; the verifier requires an explicit store and never falls back to in-memory state. The `InMemoryGrantConsumptionStore` class is process-local (a consumed grant would replay across a restart or a second replica, so it is tests/dev only); durable deployments use a `FileGrantConsumptionStore`, which claims by exclusively creating one file per grant id under a `GRANT_STATE_PATH` directory (recording the grant's expiry and pruning expired entries). The service installs `HmacGrantAuthorizer` only when BOTH a grant-issuer secret (the `grantIssuerSecret` seam or `GRANT_ISSUER_SECRET`, read at assembly time and never logged) AND durable consumption state (the `grantConsumptionStore` seam or the `GRANT_STATE_PATH` directory) are configured; a configured secret without durable state installs a deny-all authorizer and logs one static startup warning (never the secret), and a secret-less deployment installs a deny-all authorizer, so writes always fail closed. Grants reach enforcement only through the host seam (`approvalGrant`), never tool arguments; a standalone process has no path to present them, so real sends stay fail-closed until durable grant state is configured and a trusted host approval integration supplies grants.
- The fixture backend is synthetic only. Never fetch a supplied listing URL; serve only on trusted private networks. Any `Origin` header is rejected until browser access has an explicit origin policy.
- Backends expose a bounded non-empty `name`; provider failures must use validated `ProviderError` values. Search/fetch backend calls receive an abort signal and obey the configured deadline, while recognizing arbitrary promises cannot be forcibly cancelled.
- Browser runtime uses one serialized persistent-profile browser per session scope (the messenger scope is opt-in with its own profile directory); never store Facebook credentials, log cookies/localStorage/headers/page content/profile contents, or expose CDP. Browser work must honor the abort signal. The fixture backend stays the default and Facebook selection is opt-in.
- The Facebook session probe only classifies session state. A separate credential login (`src/facebook-login.ts`) may submit optional environment-supplied credentials for a plain login requirement, then wait for the out-of-band mobile approval by polling that same classification. Its single in-flight attempt is service-scoped, survives a search deadline, and is aborted and awaited on shutdown; each search waits only within its own backend budget. Approval can land on any authenticated same-origin page; the login navigates to Marketplace to verify before reporting success, and only the backend's confirming probe records `session_usable`. It never solves or bypasses a captcha or checkpoint and never automates 2FA: those states are reported so the manual re-auth flow takes over. Credentials are environment-only — never stored, logged, returned, or persisted separately; passwords are submitted unchanged, and they are read only when the Facebook backend is selected, so a fixture deployment never touches them. The resolved login URL must be same-origin with the configured base, not merely an approved origin. Ambiguous or failed probes remain `session_unknown`, never usable; Marketplace search fails closed on `session_unknown`. Keep origin injection an internal test seam, and never log page content, cookies, storage, headers, or form values.
- Facebook item IDs come only from valid extracted item URLs; never synthesize one. Search-card `state` is never `active`. Location slugs must come from configured markets and are never guessed. Unknown layouts are typed upstream errors, never empty success. Search is one page, without scrolling or pagination. Fetch accepts a listing id or canonical Marketplace item URL; it extracts the id and rebuilds the URL from the configured base, never navigating to a caller-supplied origin. Fetch uses the same fail-closed auth/checkpoint path as search. A complete listing page is returned in full, including `state: removed` when Facebook marks it so; `NOT_FOUND` applies only to an unavailable or expired shell that cannot satisfy `Listing` (no usable title, price, or location). Currency comes from an explicit price marker or a configured market resolved from the listing's own location; otherwise fetch fails closed. Do not add a second browser or auth subsystem; per-scope profile directories reuse the same session machinery.
- The shopping surface is read-only over an HTTP API (`SHOPPING_BACKEND=ebay` opt-in), scope `(ebay, default, shopping)`, risk class `read`; API credentials are environment-only, never logged or returned; no cart writes are permitted, and the fixture backend stays default.
- The events surface is read-only over an HTTP API (`EVENTS_BACKEND=ticketmaster` opt-in), scope `(ticketmaster, default, events)`, risk class `read`; the API key is environment-only, never logged or returned; no booking, reservation, or purchase is permitted; the fixture backend stays default. The Discovery API exposes event-level on-sale status and price ranges, not seat-level inventory.
- The messenger surface (`MARKETPLACE_MESSENGER=1`, scope `(facebook, default, messenger)`) exposes read-only `messenger_threads_list` and `messenger_thread_read`, plus `messenger_prepare` (risk class `prepare`: autonomous, needs no grant, sends nothing and grants no approval) wherever the conversation backend actually implements `prepareDraft`. `messenger_prepare` mints the idempotency token first, builds and validates the complete future `messenger_send` payload from it, and only then digests that validated payload, so the published `subject_digest` is exactly what `messenger_send` authorization is checked against; it must never digest the smaller prepare input, and its `status: 'draft'` / `sent: false` markers must survive any future change. An unknown thread reports `NOT_FOUND` like `messenger_thread_read`, and preparing a draft never records a message. Conversation extraction accepts only accessibility-contract signals (thread hrefs, role/aria markers, timestamps) and fails closed: an unrecognized page is a typed upstream error, never an empty success or fabricated field, and message rows without a recognizable orientation marker are skipped rather than attributed. Thread previews and message texts are untrusted seller-controlled content returned bounded and verbatim. The messenger scope exposes `messenger_send` (risk class `send`) wherever the conversation backend actually implements `sendThread`, and owns a separate interactive reauth loop driving the messenger profile with its own loopback admin port (`MESSENGER_REAUTH_ADMIN_PORT`, default 8788) and optional viewer port (`MESSENGER_REAUTH_VIEWER_PORT`), targeting the messenger inbox path by default (same landing as the session probe, so reauth never auto-opens a thread), with an opt-in `messengerReauthTargetUrl` override; its teardown joins the service's bounded, idempotent shutdown. The DOM contract is pending live-site validation — see `docs/conversation-surface-research.md` — so keep the fixture backend the reference for integration work.
- The Threads (Meta) social surface (`THREADS_BACKEND=threads` opt-in, scope `(threads, default, social)`, risk class `read`) exposes `threads_posts_list` and `threads_replies_list` over the official Threads Graph API. The connector is read-only by design and that is the contract: no publishing, no DM, no saved items, no keyword search, no external profile discovery — see `docs/instagram-threads-consumer-research.md` for the underlying capability matrix and the explicit gaps this wave leaves unfilled. Reading a Threads reply tree is a public read of already-public content, not a logged-in browser scrape, so no browser session is involved; the "session" dimension is whether `THREADS_ACCESS_TOKEN` and `THREADS_USER_ID` are configured. Both credentials are environment-only, read at assembly time, and never logged or returned in tool output; the token travels as `Authorization: Bearer …` to `https://graph.threads.net` only, with loopback accepted solely as an explicit test seam — there is deliberately no environment variable that can move the credential destination. The live `ThreadsApiBackend` is installed only through a two-part gate, checked in order: `THREADS_ACCESS_TOKEN` and `THREADS_USER_ID` must both be non-empty (a missing token or user id is a startup failure, typed `RangeError`), then `THREADS_LIVE_VALIDATED=1` must be set — an explicit operator acknowledgement that the connector was validated against the current Meta reference (operator setup and the separate live-validation checklist live in `services/marketplace/README.md`), whose absence is also a startup failure with a typed `RangeError` naming `THREADS_LIVE_VALIDATED`. The fixture backend stays default. Unknown `media_type` values map to `UNKNOWN`; missing or non-numeric reply/like counts stay `null`; timestamps that fail ISO 8601 parsing stay `null` rather than being fabricated. Post/reply permalinks and media URLs are two layers, not one allowlist. A permalink is a navigation target the provider published, so it keeps the strict exact-host `isThreadsHost` allowlist over HTTPS: `threads.net` / `www.threads.net` (legacy) and `threads.com` / `www.threads.com` (Meta's primary web host since April 2025) — exact host match, never a suffix match, so lookalikes like `threads.com.evil.example` and `notthreads.com` and any `http://` form are rejected and the bad permalink remains schema drift that fails the page. A media URL is a display artifact rather than a load-bearing fact, and real `media_url` / `thumbnail_url` values are served from Meta's media CDNs, so `isOfficialMediaHost` adds those roots (`cdninstagram.com` and its subdomains, `fbcdn.net` and its subdomains) on top of the exact Threads hosts, https-only and never a bare-suffix match; a media URL on any host outside that allowlist is DROPPED — never returned, never rewritten, never substituted — rather than discarding an otherwise valid post, while the strict schema keeps the unapproved URL out of the contract either way; the accepted predicate `isOfficialThreadsMediaUrl` (not the internal schema object) is what both the schema and the mapper's filter call, so the two cannot drift. The deliberate consequence of dropping: a suppressed media URL is indistinguishable in the output from a post that carried none, so `media_type` may still read `IMAGE` beside an empty `media_urls` — this is the one documented departure from the never-silently-swallow rule below, and the drop is deliberately silent. Media in a reply tree is third-party-authored content that merely sits on a Meta host, so an allowlisted host is never a trust signal and those URLs stay bounded and untrusted like the rest of the surface's untrusted content. Hosts are never normalized or rewritten in either layer, because rewriting a host would fabricate a navigation target the provider did not return. Both endpoint projections request `owner` alongside the documented fields, because `threads_user_id` is mapped from `owner.id` and an unrequested `owner` would map every live post to `null`; that projection is unverifiable locally, so the operator live-validation checklist names it. An absent caption is `null`, not drift: Meta permits image and carousel posts with no caption, so `text` is nullable on posts and replies and a captionless item keeps its canonical `id` and `permalink` instead of failing the whole page (never `''`, never a guessed value). `threads_user_id` is the provider's stable `owner.id`, nullable when the response carries no owner, and never the mutable `username` handle relabelled as an id. Missing `id`/`permalink` and wrong field types remain drift. Cursor following is bounded to at most 5 upstream pages per call; canonical ids are deduplicated across pages with order preserved, and both tools report an explicit `truncated` completeness indicator (`true` when a provider cursor remained or the page bound was hit, `false` when the provider page set was exhausted). Posts and replies are siblings of the listing/product/event contracts: facts only, never a comparison layer. Fail closed on missing credentials, fail closed on schema drift: a non-array `data`, or a `data` array containing a malformed/schema-drifted item, throws `ProviderError('UPSTREAM_ERROR', …)` rather than a silent empty success, while a legitimate `{data: []}` is an empty success. The same rule governs paging: a cursor we cannot read as a forward cursor (a `paging` container in a shape we do not recognize — a non-object such as a string, number, boolean, or array — an unparseable `next`, or a `cursors` field in a shape we do not recognize, such as a non-string `cursors.after`) is drift and throws rather than being reported as `truncated: false`; only an absent cursor or paging field, an explicit `paging: null`, or an explicit `cursors.after: null`, exhausts a page. The endpoints and field shapes are documented but unverified against the current Meta reference — keep the connector pointed at `graph.threads.net` and the documented fields list, and confirm against the current permissions reference before any future tool (keyword search, profile discovery, mentions) ships.
- Facebook fixture pages are synthetic and sanitized. Browser tests block all network access and must make zero Facebook requests. Never log page content, card text, hrefs, image URLs, extracted records, cookies, or storage; logs may contain only error names/codes and counts.
- Re-auth leases own the profile exclusively; admin and viewer bind to loopback only; ephemeral tokens are never logged or persisted; never automate 2FA or an interactive challenge, and never persist credentials; teardown is bounded and idempotent; assessments reset to `session_unknown` and never become usable automatically.
- Provider architecture and compatibility strategy are documented in `docs/provider-architecture.md`. New capabilities add a typed backend interface in `backend.ts`, a `domain.ts` contract, a `TOOLS` declaration with an explicit scope and risk class, provider-specific modules, and synthetic fixtures; `marketplace_status.capabilities` is the discovery surface. Preserve public tool names and bump the schema minor version for additive output changes.
- Development checks: `npm ci --ignore-scripts`, `npm run build`, `npm run typecheck`, `npm test`, and `npm run lint`.
