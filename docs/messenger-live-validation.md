# Messenger live validation (#77)

This protocol gates production thread reads, sends (#63 / PR #75), and timeout reconciliation. Inbox identity discovery (#64, implemented in PR #81) does not validate thread navigation or message extraction. No production send enablement is justified until the read gates below pass in the backend's actual browser path, with separately approved provider-observed send evidence where needed.

## Consent and privacy

Before navigating to any thread, identify the operator-approved account/session and conversation. Disclose that navigation may mark messages **Seen** and expose presence, including if Facebook redirects to another conversation. Obtain explicit read approval; record only the approval scope and date, never the account, participant, or thread key. Prefer a dedicated conversation with synthetic content. If the operator approves an existing conversation, retain structural evidence only.

Read approval does not authorize typing in the composer, Enter, clicking Send, reactions, attachments, creating a conversation, or changing account settings. Any send requires a separate concrete approval for the exact destination and delivered payload, after all read gates pass. This ticket adds no sending tool.

Do not export screenshots of conversations, accessibility trees, HTML, message text, names, raw URLs/IDs, GraphQL bodies, request payloads, cookies, headers, or storage. Project observations before returning tool output. Private values may be compared transiently in memory; do not persist them, including hashes that can correlate identities. Disable traces, videos, HAR capture, and content/debug logs for the investigation. Never copy an authenticated profile to create fixtures.

## Read gates

1. **Session and authoritative key.** Use the approved authenticated browser. Observe inbox metadata through #64's validated path, without opening threads. Keep the selected key in memory. A button's position, preview, participant name, or DOM order is not an authoritative mapping. If the approved conversation cannot be bound to a validated key, stop; do not choose a key by index. A separately operator-approved known test thread can substitute for inbox discovery.
2. **Navigation and identity.** Rebuild the URL from the configured Facebook origin and authoritative key. Record route shapes with keys replaced by `<thread>`, plus same-origin and requested-key equality booleans. Record redirect behavior without raw addresses. Check the final route and an independent rendered thread identity signal where available before exposing any content. An unchanged URL alone does not prove the rendered conversation matches. Unknown, mismatched, or ambiguous identity stops the read. Do not follow a redirect into another conversation to investigate it. A post-navigation guard prevents attribution, not a Seen receipt already emitted by navigation.
3. **Structure and direction.** Inspect bounded rendered message containers. Report roles, attribute names, generic orientation patterns with names/text replaced by placeholders, direction counts, timestamp presence/format, and attachment-container presence only. Establish sender orientation from explicit accessibility signals; alignment, color, names, and row order are insufficient. Distinguish message content from sender/status labels and controls. Unattributed rows are not messages. Account for virtualized windows and report whether the newest messages are actually included; do not call a loaded window complete history.
4. **Actual extraction path.** Compare the structural observations to `extractMessengerThreadPage` and `interpretMessengerThreadPage`. The current extractor examines every rendered message row (the conversation's `[role="log"]` rows when the page has one, otherwise document-wide) up to a 500-row scan bound, selects the newest at most 50 messages by their explicit `time[datetime]` timestamps, truncates each text to 2,000 characters, and recognizes sender-oriented row labels. DOM order never decides which end is newest. The marker must be the message row's own `time[datetime]` element — a timestamp on a nested element inside the row is not the row's own and does not place the row on the timeline — so the live pass must report, per rendered message row, whether the row itself carries such a marker. When an attributed rendered row carries no usable timestamp of its own, when the scan did not examine every rendered row, when the read collected more candidate text than its 512,000-character budget, or when the extraction cannot report its scan bounds, the newest end of the thread cannot be proven and the read fails closed with a typed `UPSTREAM_ERROR` instead of returning a window. Check whether the bounds and the timestamps include the latest outgoing message and its trailing token, and whether message rows in the deployed DOM carry explicit `time[datetime]` markers at all. A browser DOM observation alone does not verify the isolated service profile, backend navigation, settle loop, parser, or read result. Run that real path only in the approved session scope; return aggregate results, never its private message output. If the session/tooling cannot support successful extraction safely, record the refusal and its boundary; do not claim a successful production read.
5. **Token detection.** Use synthetic fixtures to check the exact bracketed token form, own-message attribution, token at a text boundary, truncation, stale/virtualized windows, attachment-only rows, and wrong-thread rejection. A seller quoting the token must not confirm the operator's send. Live token detection needs an existing operator-approved synthetic token or a separately approved send; never send merely to manufacture evidence. Record match booleans only. If no suitable token exists, live detection remains unverified.
6. **Edge cases and regressions.** Cover valid, explicit empty, shifted layout, unknown sender, attachments, wrong origin, and misdirected thread using synthetic fixtures. Only label fixtures as based on live observations when that structure was actually observed. An unobserved empty/attachment case stays unverified. Unrecognized layouts and ambiguous identity must yield a typed error, never false empty success or fabricated attribution.

## Send-confirmation gate

Inspect available delivery-state accessibility signals without touching the composer. Distinguish an optimistic/local outgoing bubble, provider acknowledgement, and delivered/read status. A successful Enter keypress, resolved send call, or bracketed token in arbitrary thread text is insufficient evidence of provider acceptance. Establish whether the own outgoing message and its acknowledgement can be correlated reliably through the real backend read path. If that cannot be demonstrated, keep the result `unknown` and production sends blocked.

Any later live send needs separate approval naming the one conversation and exact synthetic payload including its token. Use the approved host authorization flow, submit once, observe without resending, and require confirmed thread identity plus own-message/token and provider acknowledgement. A timeout never authorizes a retry. #77's read approval is not a host grant and must never be converted into one.

## Evidence record and completion

Record the date, tested code revision, browser/session category (no profile path or account name), consent scope, route patterns, identity-check booleans, bounded role/direction counts, generic timestamp format, attachment/empty classification, token-match boolean, and provider-acknowledgement classification. Mark every gate **observed**, **synthetic only**, **pending**, or **failed**, with a short reason. Unknown is not false and synthetic success is not live proof.

Store only sanitized findings and fixtures. Run the relevant regressions from the repository root, review the diff for private data, and verify every #77 acceptance item independently. #77 explicitly permits message parsing, sender orientation, and token detection to fail closed with diagnostics. A negative validation can complete this investigation when controlled navigation, actual-page refusal, synthetic regressions, and the downstream blocker are documented and verified. Closing #77 does not establish working production reads or authorize sends. #63 / PR #75 must retain the unresolved extraction and provider-confirmation requirements regardless of this ticket’s state.

## Investigation result (2026-10-11)

This is a **negative live validation**: navigation worked for the approved conversation, but its message layout is unsupported. The implementation refuses that layout explicitly. Successful production extraction and provider-confirmed sending remain blocked.

- Initial comparison used `da7c512`, with the same extractor/parser at base `db226be`. The patch adds structural diagnostics and exact route matching; it does not infer article sender attribution.
- The operator approved existing-conversation inspection after Seen/presence disclosure, authenticated the in-app browser, and selected the known test conversation. No composer input, reaction, attachment, or send occurred.
- The inbox had 24 conversation buttons, zero canonical thread anchors, and no authoritative key attributes. No positional mapping was inferred. The selected conversation’s **Chat settings → Open in Messenger** link supplied its canonical key transiently.
- Rebuilding `/messages/t/<thread>/` reached the expected origin and exact key. A separately opened `/messages/e2ee/t/<thread>` route and canonical route shared all 10 loaded provider message-control labels, compared only in memory. This independently corroborates the selected rendered conversation for this sample; it does not establish GraphQL-key equivalence, complete history, or every intermediate redirect. The canonical route stayed canonical.
- The rendered log used unlabeled articles, nested headings, and message-action controls instead of attributed role rows. No `time[datetime]` elements were observed. Nested accessibility labels contained generic `message sent … by …` patterns, including `by you`, but their full grouping and sender/content contract were not verified. They are not used to fabricate attribution.
- The updated extractor’s logic, evaluated read-only against the actual canonical page, reported authenticated/main present, no login/challenge signal, a message log with articles, 16 scanned/unattributed role rows, and **zero extracted messages**. Only these structural booleans and counts were returned. This verifies the extraction refusal on the actual page, not the entire isolated service session.
- The deployed Messenger list and read tools each refused with `CAPTCHA_REQUIRED` and returned no conversation data. The isolated service profile is distinct from the operator browser; its authentication boundary prevented a live content-path test. The tool error alone does not prove that an interactive CAPTCHA was visible.
- The parser now rejects article-based logs with a static unsupported-layout diagnostic, including when unrelated attributed rows exist elsewhere. A synthetic explicit-empty log also returns an unverified-layout error. A route with an extra path segment after the requested key is now rejected; previously the prefix guard accepted it. Wrong origin, wrong key, inbox redirects, and encrypted route shapes remain fail closed.
- Synthetic fixtures exercise valid legacy rows, shifted/unsupported layouts, empty and attachment-only cases, unknown senders, misdirected routes, and token bounds through extraction/parser/backend tests. Token text is bounded at 2,000 characters and the first 50 extracted messages; a token outside those bounds is not detected. A quoted token in an incoming message retains incoming attribution and supplies no delivery confirmation. These fixtures contain invented content only; live empty/attachment behavior and newest-window completeness were not established. (That window was head-anchored at the time; #146 later anchored it on the newest end by explicit timestamps, with a fail-closed read when the newest end cannot be proven.)
- No reliable provider acknowledgement was established from the inspected accessibility signals or current backend read path. The send-confirmation result is **unknown**. Enter, optimistic bubbles, and arbitrary token text must not become confirmation. No live token was planted or send attempted.
- No private conversation text, names, identifiers, raw page dumps, or authenticated profiles were stored in the repository or evidence record.

The negative result satisfies #77’s fail-closed validation alternative. It does not resolve the unsupported layout or provide the evidence required to enable production sends.
