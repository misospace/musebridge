Parent: #188 (Companion transport research). Status: **decision record. A self-hosted Messenger transport built on `mautrix-meta` is technically feasible, and this document records how. Decision (revised 2026-11-03): GO for an experimental, disabled-by-default, explicit opt-in `mautrix-meta` provider**, under the operator's bounded exception recorded on #193 (2026-11-02). The standing unofficial-protocol rejection in `messenger-consumer-research.md` §2 remains the default policy, and this GO is a narrow exception for `mautrix-meta` only, not blanket approval for arbitrary unofficial or private Meta APIs. ## 2. Package boundary (question 1)

`grep -rl bridgev2 pkg/messagix` at the pinned revision matches five files, the same five files the #188 review counted at `9c4954a7`. The set is unchanged; do not trust the count without re-running the grep at your own pinned SHA.

| File | Reference | Library surface? |
|---|---|---|
| `pkg/messagix/bloks/cmd/main.go` | comment only: "See the actual login flow integrating with bridgev2 for the latest best practices." (`bloks/cmd/main.go:108-110`) | no; standalone `package main` debug command |
| `pkg/messagix/bloks/selenium.go` | real: imports `bridgev2` and `event`; builds `bridgev2.LoginStep` values with `LoginStepTypeUserInput`, `LoginStepTypeCookies`, `LoginInputFieldTypeSelect/Username/Password/2FACode/CaptchaCode`, and tags captcha images and audio with `event.MsgImage`/`event.MsgAudio` | yes; `bloks` is imported by `pkg/messagix/messengerlite.go`, `pkg/connector/login.go`, and others |
| `pkg/messagix/bloks/selenium_platform.go` | real: `bridgev2.RespError` value fields (`InvalidUsername`, `MandatoryOAuth`, `NoSupportedMFA`, `ReCaptcha`, `NoSMSAvailable`, `MandatoryPasskey`, `AccountRecovery`) | yes; part of `bloks` |
| `pkg/messagix/loginerrors/errors.go` | real: the whole file is a set of `bridgev2.RespError` values, for example `MissingCookies = bridgev2.RespError{ErrCode: "FI.MAU.META_MISSING_COOKIES", ...}` (`errors.go:10`), plus four helper functions (`WithMessage`, `Uninformative`, `PasswordResetRequired`, `AccountRecovery`) | yes; imported by the login paths |
| `pkg/messagix/messengerlite.go` | real but narrow: one signature, `func (m *MessengerLiteMethods) DoLoginSteps(...) (*bridgev2.LoginStep, *cookies.Cookies, error)` (`messengerlite.go:374`) | yes; core package |

The shim is small and typed. A fork must supply roughly 21 plain identifiers from `bridgev2` plus two from `mautrix/event`: 10 types (`RespError`; `LoginStep`; `LoginUserInputParams`; `LoginInputDataField`; `LoginUserInputAttachment`; `LoginUserInputAttachmentInfo`; `LoginCookiesParams`; `LoginCookieField`; `LoginCookieFieldSource`; `LoginDisplayAndWaitParams`), 10 constants (`LoginStepTypeUserInput`, `LoginStepTypeCookies`, `LoginStepTypeDisplayAndWait`; `LoginInputFieldTypeSelect`, `LoginInputFieldTypeUsername`, `LoginInputFieldTypePassword`, `LoginInputFieldType2FACode`, `LoginInputFieldTypeCaptchaCode`; `LoginCookieTypeSpecial`; `LoginDisplayTypeNothing`), the error value `ErrLoginStepCancelled` (used at `selenium.go:2121-2129`), and the `event.MsgImage`/`event.MsgAudio` attachment-type constants (`selenium.go:1241`, `1251`). None of the types carry behavior; they are login-UX shapes that flow to a user interface. A fork that defines these identifiers locally severs `maunium.net/go/mautrix` from the messagix build completely. The heavier dependency that stays is `go.mau.fi/whatsmeow`: `pkg/messagix/client.go` imports it unconditionally (`client.go:16-17`) for the device store, and the E2EE (Armadillo) pipeline (`e2ee-client.go:27-29`, `e2ee-register.go:39-42`) and native push (`nativepush.go:18`) use it further.

`pkg/connector`'s `MetaConnector` is a different story. `MetaConnector` itself asserts 6 `bridgev2` interfaces (`bridgev2.NetworkConnector`, `MaxFileSizeingNetwork`, `NetworkResettingNetwork`, `DirectMediableNetwork`, `TransactionIDGeneratingNetwork`, `IdentifierValidatingNetwork`), and its per-user client `MetaClient` asserts 19 more; the package carries 54 interface assertions over 40 distinct interfaces, the rest on the remote-event types (11 distinct `bridgev2.RemoteEvent*` interfaces in `connector/events.go`). The connector holds a `*bridgev2.Bridge`, drives `bridgev2.UserLogin` and portal state, and `pkg/msgconv` converts events with a `*bridgev2.Portal` in hand. Driving `MetaConnector` without Matrix means reimplementing bridgev2's host side. That is not a shim. It also matters for boundaries: `MetaClient` implements `CredentialExportingNetworkAPI`, and `ExportCredentials` returns the cookies and the native session together (`connector/client.go:184-196`). That is a surface the no-credential-export rule must never reach, and a messagix-only fork does not carry it. The conclusion matches #188's open question: **a non-Matrix consumer must target `pkg/messagix` directly**, not `MetaConnector`. The repo itself shows the low-level path is Matrix-free: `cmd/lscli` imports only `pkg/messagix` packages (`lscli.go:18-21`), though it is a decoder for captured payloads, not a live driver.

## 3. Auth modes that work today (question 2)

`pkg/connector/login.go` declares four flows (`login.go:32-35`):

| Flow id | Credentials | Resulting session material |
|---|---|---|
| `facebook` | cookies from facebook.com: `xs`, `c_user`, `datr` (`cookies.go:48`) | web session cookies |
| `messenger` | cookies from messenger.com, same required set | web session cookies |
| `messenger-lite` (iOS) | username and password, plus interactive MFA steps | web session cookies (no native session persisted) |
| `messenger-lite-android` | username and password, plus interactive MFA steps | cookies plus `types.NativeSession{AccessToken, AppID, DeviceID, FamilyDeviceID, MachineID}` (`types/native_session.go:5-11`) |

Native login is real native authentication, not a browser emulation: `MessengerLiteMethods.DoLoginSteps` (`messengerlite.go:374`) runs Meta's Bloks app-document protocol through an in-process interpreter (`bloks/interp.go`, `bloks/selenium.go`; despite the filename there is no Selenium or webdriver code). The device identity is generated locally, not bound to real hardware: `m.deviceID = uuid.MustParse(m.browser.Bridge.DeviceID)` with the source comment "these values are generated by us, they are known safe" (`messengerlite.go:381-385`). The password is encrypted with a key fetched per device: `FetchLightspeedKey` (`messengerlite.go:130`) sends the generated `device_id` and `machine_id` in its request parameters (`messengerlite.go:137-141`).

Challenge handling splits in two, and both halves matter for this repo's rules:

- During native login, the flow can resolve MFA interactively: TOTP (`selenium.go:1587-1597`), backup codes (`selenium.go:1663-1670`), captcha with image and audio attachments (`selenium.go:1239-1261`), approve-from-another-device as a display-and-wait step (`selenium.go:2102-2110`), and verification-method selection (`selenium.go:1438-1444`) are all typed login steps. The connector exposes these to its host through the user-input, cookies, display-and-wait, and step-cancel login flow interfaces (`login.go:462-465`). A host must present these steps to a human operator; automating them stays out of scope.
- Outside login, and on the cookie path, blockers surface as typed errors only. `loginerrors/errors.go` defines `Challenge`, `Consent`, `Checkpoint`, `TokenInvalidated`, `NoSupportedMFA`, `ReCaptcha`, `AccountSuspended`, `RateLimited`, and more (`errors.go:10-30`), and their message text sends the user to the official app: "Checkpoint required, please check the official website or app and then try again" (`errors.go:13`). This matches the existing no-challenge-automation rule exactly.

Session durability is the weak point, and it is a design input, not a blocker. Invalidation is detected loudly: `ErrTokenInvalidated` (`httpclient/http.go:362`), a redirect checker that fires when the `xs` or `sessionid` cookie disappears (`http.go:459-464`), and socket close code 4003 (`dgw.CloseStatusUnauthorized`, `dgw/frames.go:35`) mapped to a permanent error that stops reconnection (`client.go:283-287`). There is no automatic token refresh anywhere in the source. When a session dies, the host must re-run a login flow. So the durable asset is the persisted session material (cookies, or the Android native session), and a GO design must state how that material is stored and re-login is driven.

## 4. Read, history, and search capability (question 3)

History is the strongest part of the surface, and its semantics are explicit:

- On connect, the client syncs numbered LightSpeed "databases" (sync groups) with per-group cursors; the Facebook minimum set is `minimalFBSync = []int64{1, 2, 95, 104}` (`socket.go:31`). This gives the current inbox window incrementally.
- Deeper history is fetched on demand by message-range paging: `FetchMessagesTask` with a reference timestamp and message id (`connector/backfill.go:144-156`), joined across successive `table.UpsertMessages` ranges until `Range.HasMoreBefore` turns false or the requested count is reached. Range and gap semantics are explicit in `LSInsertNewMessageRange` (`table/messages.go:224-234`), and the collector guards cursor monotonicity ("history cursor did not move backwards"). Depth is bounded by server availability; the source documents no cap, and none can be assumed.
- Encrypted history is supported through the secure-history protocol: epoch keys, archive decryption, and OPAQUE-based PIN verification and `RecoverPIN` against the recovery server (`pkg/messagix/securehistory/`, `vesta.go`; the bridge offers a 6-digit PIN login step, `connector/login_history.go:26-47`).

Search is narrower than the word suggests, and a contract built on it must say so. The only search surface is a server-side LightSpeed task (`socket.SearchUserTask`, `socket/contacts.go:40-51`) that returns people, groups, and pages (`LSInsertSearchResult`, `table/search.go:17-55`) with optional message context fields (`ContextLine`, `MessageId`, `MessageTimestampMs`, `search.go:26-28`). Free-text message search is not implemented: the type enum and result table exist, but no call in `pkg/messagix` or `pkg/connector` issues a message-body search. Coverage truthfulness for this repo means: search over this transport is recipient and thread discovery, never a message-content index.

The read surface covers: message bodies with sender, timestamp, reply metadata, and unsent markers (`table/messages.go`); reactions with actor and timestamp (`messages.go:408` and `connector/backfill.go:390-396`); read and delivery receipts (`table/threads.go:197`, `314`); typing indicators; attachment metadata (`XMAAttachments`, `BlobAttachments`, `Stickers`); thread metadata and participants (`threads.go:40`, `163`). Marketplace is part of the surface: `MARKETPLACE ThreadType = 5` and `MARKETPLACE_SEND_MESSAGE ThreadSourceType = 1245186` (`table/enums.go:259`, `106`), with a `marketplace_space` connector config (`connector/config.go:35`).

Writes exist but are out of scope for a read-only proof: send text and media, edit, unsend, react, mark read, typing, membership and group operations, block, and polls, each as a named socket task (for example `SendMessageTask`, `EditMessageTask`, `DeleteMessageTask`, `SendReactionTask`, `ThreadMarkReadTask`; `table/threads.go`, `messages.go`, and the `HandleMatrix*` handlers in `connector/handlematrix.go` that drive them).

## 5. Local state and key material (question 4)

`pkg/messagix` persists nothing on its own: there is no database, no file writes, and no filesystem reads or writes in the library surface (the only `os.Open` calls in the directory sit in two standalone `package main` debug commands, `bloks/cmd/main.go:91` and `bloks/cmd_new/main.go:76`). Persistence is delegated to the host, and the two layers delegate differently:

1. **The messagix contract** is one JSON blob: `Client.DumpState()`/`LoadState()` (`client.go:140-177`) holds provider configs, per-sync-group cursors, and a timestamp the host must treat as stale after 24 hours (`MaxCachedStateAge`, `client.go:152`). A bare host can store it anywhere, including nowhere.
2. **Session and key material** is the host's own store. In mautrix-meta, the connector persists it as login metadata (`metaid/dbmeta.go:51-67`): platform, cookies, the native session, push keys, and `HistoryDevice`. `pkg/metaid` is connector-side; a bare messagix host never touches it and must define its own session store instead.

The key material that a host must persist for the encrypted path is real and long-lived: `securehistory.Device{StoragePublicKey, StoragePrivateKey, MailboxRootKey, OCMFClientState, Epochs}` (`securehistory/device.go:79-87`), where each epoch carries a `RootKey` (`device.go:73-77`). The E2EE device identity additionally lives in a whatsmeow `store.Device`. Message content is a different category: messagix never stores it. Tables arrive over the socket and are handed to the host; the message store in mautrix-meta belongs to bridgev2, and `pkg/metadb` (thread anchors, id mappings, reconnection state) is connector-side and not required by a bare messagix client.

Mapped onto this repo's rules: a read-only history PoC **can satisfy the no-content-persistence rule without an exception**. It must persist session material, cursors, and key material, and those must be handled like credentials: operator-owned secrets, never logged, never returned, never exported. The repo already has the storage precedent: the messenger browser scope persists session cookies to a dedicated profile directory (`MESSENGER_PROFILE_DIR`, default `~/.marketplace/browser-profile-messenger`), so a transport scope would need its own equivalent. Message text stays in memory only and is returned bounded and verbatim. The deliberate choice a GO issue must record is session shape: a stateless per-request client (no long-lived socket, re-sync each call, cursors discarded) is simplest but re-pays sync cost and multiplies request volume against the same account; a long-lived session holds cursors and keys but is a stateful background actor. Both are consistent with the no-content rule; the choice must be explicit, not defaulted. One more contract point follows from default end-to-end encryption: a PoC that skips the E2EE path reads only unencrypted threads, so an honest history capability needs the E2EE pipeline (device registration, secure-history keys, and the PIN recovery step) and its key-material state.

## 6. ToS and account risk (question 5)

Native login does not remove the legal exposure. Meta ToS §3.2(3) forbids accessing or collecting data from Meta products "using automated means (without our prior permission)" (cited and archived in `messenger-consumer-research.md` §2), and a programmatic client is automated access whether it presents cookies or a native login. What native login changes is the aggravator, not the category: it removes the credential-export problem of the cookie path, because the user authenticates directly with username and password and the resulting session is minted by that login.

The ban surface differs in kind from the browser path. The browser path operates the operator's real browser session on the real site. The native path presents an emulated Messenger Lite client with self-generated device UUIDs speaking the Bloks protocol; the source's own error set names the failure modes an account can hit (`Checkpoint`, `AccountSuspended`, `RateLimited`, `NoSupportedMFA`, `MandatoryPasskey`). The interactive MFA steps keep a human in the loop at login, which is consistent with this repo's rules, but they do not make the client sanctioned. Comparing detection risk between the two paths is a structural judgment from source, not an observed fact: the source shows what each client presents, not what Meta's enforcement tolerates. On the axes under this repo's control (session provenance, client identity, request volume), the shipped header-menu tools carry the smaller footprint: one authenticated page load, verified non-opening, read-only, no client identity beyond the session. The standing rejection of unofficial protocol libraries in `messenger-consumer-research.md` §2 covers this transport class and stays the default policy. The operator, who alone can change that boundary, recorded a bounded exception on 2026-11-02 (#193): Musebridge may carry `mautrix-meta` as an experimental, disabled-by-default, explicit opt-in provider when the operator acknowledges this account-risk boundary in the same act that enables it. Section 9 states the conditions.

## 7. License (question 6)

`mautrix-meta` is licensed AGPL-3.0 (`LICENSE`, 661 lines of the standard FSF text; the repository declares no SPDX identifier, and the text carries the "any later version" clause) with a narrow exceptions file: the developers grant Beeper the right to embed the program in Beeper clients and servers, and use and distribute the collective work "without applying the license to the whole"; and Element the right to distribute compiled binaries as part of Element Server Suite and other server bundles "without applying the license" (`LICENSE.exceptions:3-8`). Both exceptions are conditioned: "any modifications to the source code of mautrix-meta remain publicly available under the terms of the GNU AGPL version 3 or later" (`LICENSE.exceptions:10-12`). Musebridge holds neither exception.

Musebridge currently carries no license at all (no `LICENSE` file, no `license` field, checked 2026-11-03). The three adoption shapes from the issue have these consequences:

1. **Embed or modify inside Musebridge.** Musebridge becomes a combined work under AGPL-3.0: the repository must adopt the license, and every modification to the derived code must be published. This changes the license of the whole repo and is the highest-commitment option.
2. **Run mautrix-meta unmodified as a separate service.** A separate, unmodified program is a separate work; Musebridge stays license-neutral and talks to it over a boundary. But the moment the service needs an interface mautrix-meta does not expose, the service is modified, and option 3 applies.
3. **Run a modified separate service (fork).** A fork that adds a shim and a host-facing API is a modified version of an AGPL work. AGPL §13 requires offering its complete source to users who interact with it over a network. Musebridge itself stays license-neutral; the fork is published under AGPL-3.0.

Option 3 is the least-committal shape that fits the Section 2 conclusion (the shim lives in a fork anyway) and keeps the Musebridge license question open. The operator decision on #193 and the architecture boundary in #195 point the same way: prefer an isolated service/provider boundary for the AGPL component rather than absorbing it into the existing Node service, and document the chosen AGPL-compliant shape before code from the upstream project is incorporated or modified. Option 3 remains the recommended shape; #195 requires that the shape be documented and reviewable before implementation code lands.

## 8. Direct use versus fbchat-v2 (question 7)

`fbchat-v2` (Apache-2.0, active: v2.3.4, head `b94a37d9` dated 2026-10-21) vendors `mautrix/meta` as a git submodule at `bridge-e2ee/meta` (checked at `b94a37d9`), wraps it behind a Python API plus a Go E2EE bridge, and adds nothing over the upstream transport. Using it would add a wrapper layer, pin the transport to the wrapper's release cadence, and put the Section 2 shim one layer further from our control. Direct use of a fork is the better shape for a bounded proof: fewer moving parts, one repository to pin, and the shim and the MCP surface live in the same codebase.

## 9. Decision

**GO for an experimental, disabled-by-default, explicit opt-in `mautrix-meta` provider.** The operator recorded this decision on #193 on 2026-11-02, and #195 is the bounded implementation/proof issue. The first version of this document recorded NO-GO, on the boundary row in `messenger-consumer-research.md` §2 ("unofficial protocol libraries / scrapers — rejected, ToS violation and ban risk"). That row stands as the default policy; what changed is that the operator, who alone can change it, granted a narrow bounded exception for `mautrix-meta`. The policy the operator set:

- **GO** for an experimental, disabled-by-default, explicit opt-in `mautrix-meta` provider.
- Browser-backed Messenger remains the default and fallback.
- Enabling `mautrix-meta` requires explicit provider selection **and** explicit operator acknowledgement of the Meta account-risk boundary.
- This is a narrow exception for `mautrix-meta`, not blanket approval for arbitrary unofficial or private Meta APIs.
- The first implementation is **read-only**: thread, history, and backfill only.
- Native login only for the proof; no exported browser cookies.
- Human-driven MFA and challenge handling only; no challenge or checkpoint automation.
- No persistent message-content index.
- Writes remain out of scope and continue to require separate approval and boundary work under the existing action model (`provider-action-boundaries.md`).
- Prefer an isolated service/provider boundary for the AGPL component rather than absorbing it into the existing Node service (Section 7, option 3).

The blocker was never engineering, and Sections 2 through 5 still show that: the narrowest capability (message-history read and backfill over MCP) is technically feasible on a `pkg/messagix` fork with a small typed shim, and Section 6 keeps the residual account risk stated in full so the operator accepts it knowingly. Until the #195 proof ships, the shipped header-menu tools (`consumer_threads_list`, `consumer_threads_search`) remain the only personal-Messenger surface.

**Implementation contract carried into #195, recorded so a future run does not repeat this evaluation:**

- A `pkg/messagix` fork with the shim from Section 2, behind an isolated provider/service boundary per Section 7 (option 3), with the AGPL-compliant shape documented before upstream code is incorporated or modified.
- Native login only (`messenger-lite` or `messenger-lite-android`; the cookie flows are excluded because their login step asks for cookies or a cURL command copied from a browser (`connector/login.go:218`), which is the credential export the boundary forbids), with session material stored as operator-owned secret state.
- History reads via `FetchMessagesTask` backfill using the explicit `HasMoreBefore`/`HasMoreAfter` range semantics, with bounded page counts and an explicit `complete: false`-style disclosure when a range is not exhausted, per the repo's coverage vocabulary.
- Search scoped and disclosed as recipient/thread discovery only, per Section 4.
- No message-content persistence, with the session-shape choice from Section 5 made explicit; E2EE path included or the coverage limitation disclosed, per Section 5.
- Synthetic-first tests over synthetic LightSpeed table fixtures with zero Facebook requests (any real-payload capture is a separate operator-approved step); typed challenge errors only, no automation; live validation only after separate operator approval.
- The provider cannot start without both explicit provider selection and explicit risk acknowledgement; the browser provider must stay usable when the experimental provider is disabled or broken.

**Reconsideration trigger:** superseded on 2026-11-02 by the operator's bounded exception recorded on #193 and the opening of #195; the §2 row itself stands unamended as the default policy (see §9). Re-open the decision if Meta sanctions a personal-account protocol that makes this transport unnecessary, or if the operator withdraws or narrows the exception.

## 10. Verified versus assumed

**Verified (source and public data at the pinned revisions):** the symbols, quoted strings, and file references in Sections 2 through 8, read directly from `mautrix/meta` at `175f3d11540d8c27ee50bbb87f482a6a4ee195b4`, with line ranges re-checked and corrected in this revision; the license text and exceptions; `fbchat-v2`'s submodule and release state at `b94a37d9`, checked through the GitHub API (repository tree, `.gitmodules`, and commit list at that ref); Musebridge's missing license file and field; the ToS and Developer Policies citations reused from `messenger-consumer-research.md` §2, which captured them from the cited pages or their archive copies.

**Assumed or unverified (must not be treated as fact):** how native-login sessions behave in practice under checkpoints, token invalidation, or rate limiting (the source shows the flows and typed errors, not their live outcomes); whether Meta tolerates a short-lived, minimal-sync client (no rate or session documentation exists in the source); the practical depth limit of history paging; whether the iOS flow can ever produce a refreshable long-lived token (the source path ends in web cookies); the share of Messenger threads that remain unencrypted (no source establishes a proportion); whether whatsmeow's own module graph pulls any Matrix code into a fork that has severed its direct mautrix imports (unresolved; whatsmeow's purpose here is Signal-protocol and push, not Matrix); how long upstream keeps the `bridgev2` shim surface at its current size (the API is unversioned and the set drifts); and whether E2EE-only threads degrade any part of the unencrypted read surface in practice.

**Deliberate gaps:** no live probing of Meta, mautrix-meta, or any third party; no credentials, cookies, keys, or message content handled; no dependency added to Musebridge; Instagram surfaces (`instameow`, `igconnector`) not analyzed, out of scope.
